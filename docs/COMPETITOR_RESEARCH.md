# Spreadsheet alternatives and product acceptance criteria

Research date: **2026-09-07**. Audience: 900Sheets maintainers and contributors.

900Sheets should earn adoption by making ordinary spreadsheet work dependable on constrained computers: enter a register, calculate totals, correct mistakes, exchange a file, print it, and recover after an interruption. A long feature list does not establish that these tasks are usable. The recommendations below prioritise those complete workflows.

## Scope and evidence

This review covers Microsoft Excel, Apple Numbers, Google Sheets, LibreOffice Calc, ONLYOFFICE Desktop Editors, and Gnumeric. Vendor and project documentation establishes published capabilities and requirements; it does **not** establish comparative speed, accessibility conformance, or successful file fidelity on a particular machine. No competitor was benchmarked or manually tested for this research. No prices, market shares, or country-specific adoption claims are assumed.

The 900Sheets baseline comes from the repository [README](../README.md), [user guide](USER_GUIDE.md), [compatibility contract](COMPATIBILITY.md), and [quality gate](QUALITY_GATE.md), read on the research date. The mission is free, local-first editing without an account, subscription, telemetry, or continuous internet. Existing safeguards include bounded transactions, crash recovery, rotating backups, sparse storage, grid virtualization, and export preflight. Those are useful design foundations; they are not measurements of performance on older hardware.

The recommendations below inform the canonical [product acceptance criteria](PRODUCT_CRITERIA.md). They are **proposed verification work**, not claims that the current release passes. Actual results belong in the compatibility matrix or a dated performance report with the tested commit and artifact. Keep resource thresholds in the product criteria rather than maintaining competing budgets here.

## Accessibility is a workflow, not a label

Excel publishes [screen-reader workflows](https://support.microsoft.com/en-us/accessibility/excel/use-a-screen-reader-to-explore-and-navigate-excel) and [accessibility tools](https://support.microsoft.com/en-us/accessibility/excel/accessibility-tools-for-excel). Apple documents [creating and editing a Numbers template with VoiceOver](https://support.apple.com/en-gb/guide/numbers/tan70326493e/mac). Google provides [Sheets screen-reader instructions](https://support.google.com/docs/answer/1632199?hl=en-GB). ONLYOFFICE Docs describes cell/sheet announcements and supported readers in its [accessibility documentation](https://helpcenter.onlyoffice.com/docs/userguides/accessibility/screen-reader.aspx); those web-editor statements are not verification of every desktop package. This research does not establish current Gnumeric or LibreOffice accessibility conformance.

**Recommendation:** verify that a person can create a workbook, enter and correct formulas, navigate a range, save, recover, and export using a keyboard and a named screen reader. Automated ARIA assertions alone cannot establish those outcomes. If Tab moves between cells, provide and document another reliable way to leave the grid; if Tab leaves the grid, communicate that departure from common spreadsheet behaviour. Never trap a keyboard user to imitate another product.

## Prioritised acceptance criteria for 900Sheets

### P0: trust and mission requirements

| ID | Acceptance criterion | Required evidence |
| --- | --- | --- |
| TRUST-01 | Native Save, Save As, Open, New, and Close preserve the correct workbook and dirty state even when a save is slow or fails. Failed replacement leaves the previous file readable; backup failure is distinguished from primary-save failure. | Automated failure/race fixtures plus a packaged-app save/reopen check. Include permission denial, disk-write failure, cancelled picker, and replacement during an in-flight save. |
| TRUST-02 | An interrupted dirty session can be recovered without deleting unrelated work. Undo/redo restores data, formulas, and relevant formatting; rejected oversized operations leave the workbook unchanged. | Crash/restart and bounded-operation fixtures. Record the recovery interval, expected latest recoverable edit, and actual observed result. |
| OFFLINE-01 | A user with the complete distribution can install, launch for the first time, create from a bundled template, edit, save, reopen after reboot, recover, and export with network access disabled and no product account. | A clean-machine run for each claimed platform; record whether a runtime had to be supplied separately. Blocked network requests must not prevent completion. |
| COMPAT-01 | Opening/exporting a supported foreign file never implies complete fidelity. Features known to be discarded must be reported before the destructive conversion is accepted; original input remains recoverable. | Invented XLSX fixtures containing supported formulas/styles and unsupported objects. Compare formulas, results, cell types, sheet names, and feature metadata after reopen in 900Sheets and an external app. State Excel desktop results separately from LibreOffice results. |
| EDIT-01 | Entry, range selection, copy/cut/paste, relative and absolute formula references, fill, and undo behave consistently between the grid and formula bar. Sorting keeps each record's related cells together. | End-to-end register and budget tasks, including cross-sheet references, mixed text/numbers, empty cells, quoted TSV, multiline cells, formula errors, and filtered data. Unsupported modes need clear feedback. |

### P1: practical daily use

| ID | Acceptance criterion | Required evidence |
| --- | --- | --- |
| UX-01 | At 1024×768 and 1366×768, a new user can identify the active cell, formula/value, sheet, filename, unsaved changes, and next save action. Frequently used controls remain available; text is legible, focus visible, and dialogs operable at 200% zoom. | Packaged-app screenshots and keyboard walkthrough on each claimed platform. Review blank, populated, error, and busy states, not only a promotional template. |
| UX-02 | Complete four local tasks: attendance register, stock list, household/school budget, and a community expense report. Users can enter data, calculate totals, format dates/numbers, filter/sort, correct an error, save, and produce a readable one-page or intentionally paginated PDF. | Invented fixtures with expected results and task instructions. Observe at least five representative users across two roles; target four successful unaided completions per task and record failure causes. This is a proposed usability study, not existing validation. |
| ACCESS-01 | Core tasks work without a mouse and with a documented screen-reader/OS combination. Selection and errors are not conveyed by colour alone; dialogs restore focus; reduced motion and high contrast remain usable. | Automated keyboard checks plus manual NVDA/Windows and VoiceOver/macOS runs for released platforms. Add Orca/Linux when shipping a Linux package. Record failures rather than claiming blanket compliance. |
| LOCALE-01 | Dates, decimal separators, currencies, CSV delimiters, Unicode names, leading-zero identifiers, and text beginning with `=` have explicit, predictable handling. Templates do not silently assume a currency or translate only part of an error message. | English/Swedish/Spanish fixtures plus at least one reviewed target-community locale. Test ambiguous dates, semicolon CSV, decimal commas, and non-Latin text. Document any unsupported import encoding or formula syntax. |
| FEEDBACK-01 | Noticeably long imports, calculation, sort, and export indicate progress or activity and keep users informed. Cancellation, where offered, leaves the workbook consistent. Budget rejection explains how to reduce the task. | Slow-operation fixtures with cancellation and failure checks. Users must not interpret a blocked main thread as successful completion or be invited to repeatedly click a busy action. |
| DOCS-01 | Every published capability has a discoverable task guide and accurate compatibility boundary. Every supported installer has first-run, update, recovery, and uninstall instructions that can be obtained for offline use. | Documentation links and release evidence checked on the exact published version; no screenshots with real personal data. Update docs alongside behaviour changes. |

### P1: performance evidence

The [product criteria](PRODUCT_CRITERIA.md#target-machines-and-workloads) define the two-core, 4 GiB reference machine, 2 GiB exploratory tier, invented workloads, and provisional [resource gates](PRODUCT_CRITERIA.md#resource-gates). A fast developer laptop, CPU throttling, or a memory-limited virtual machine can find regressions but cannot replace a physical reference-machine result. These engineering targets are project choices, not numbers established by competitor sources.

Measure the application **and all WebView/helper processes** with a consistent documented OS metric. Publish median, maximum, and edit-latency percentiles with the exact fixture, artifact hash, and machine configuration. Include recovery writes and backup work in the investigation; a fast grid does not compensate for repeated whole-workbook serialization during typing. Separate installation size from app assets and warm starts from cold launch.

Supplement the ordinary-workbook tests with a sparse high-coordinate fixture, a dependency-heavy fixture, and 20 open/close cycles. Observe peak and post-idle memory, work cancellation, and sustained memory growth. A supported grid address is not a promise that a dense sheet of that size is practical. Revise budgets openly after real measurements, explaining the tradeoff rather than silently raising limits.

## Distribution details that affect the mission

Tauri's default Windows installer downloads WebView2 when it is absent. Embedding its bootstrapper still needs internet. Tauri offers `offlineInstaller` to include the runtime installer, with a larger download. Choose and label the distribution deliberately; test both an already-provisioned computer and a clean offline computer. Count prerequisites in the download/storage story. [Tauri Windows installer options](https://v2.tauri.app/distribute/windows-installer/)

The audited 900Sheets [Windows bundle configuration](../apps/desktop/src-tauri/tauri.conf.json) now selects `offlineInstaller`. This is a statically inspected setting, **not a verified Windows offline installation**. Tauri estimates approximately 127 MB additional payload for this mode; publish the actual built installer size and test the release artifact on a disconnected machine without WebView2. [Tauri offline installer documentation](https://v2.tauri.app/distribute/windows-installer/#offline-installer)

For Linux AppImages, Tauri recommends building on the oldest intended base with WebKitGTK 4.1 and cites Ubuntu 22.04 and Debian 12 as suitable baseline examples. A build made on a newer distribution can require a newer glibc than the intended machine has. A Linux source-build check therefore does not establish a working downloadable Linux product. [Tauri AppImage limitations](https://v2.tauri.app/distribute/appimage/)

**Recommendation:** publish a precise support matrix by artifact, architecture, OS baseline, WebView/runtime, installation permissions, and verification status. Prioritise a maintainable Linux package path for reusable older PCs alongside the existing Windows workflow. Do not equate supporting an obsolete OS with supporting older hardware, and do not claim 32-bit support without a built and tested 32-bit artifact.

## Positioning and next work

The defensible product promise is a free, understandable local spreadsheet for everyday records and calculations, with reliable saving and explicit exchange-format limits. Claims such as “faster than Excel,” “lightest spreadsheet,” “fully Excel compatible,” “accessible to everyone,” or “works on any old computer” require evidence this research does not supply.

Build and review in this order: resolve data-loss/calculation defects; make primary editing and save workflows coherent; enforce offline/resource bounds; validate representative tasks on packaged reference systems; then expand compatibility and advanced features. Product polish includes empty/error/busy states, consistent menus, readable templates, and accessible output, not only colours and icons.

Evidence sources used: repository documentation and current official public product/project documentation, linked next to the claims they support. CRM, customer-call, and internal sales sources are not relevant to this engineering comparison. Remaining material gaps are physical older-hardware measurements, clean-machine offline installs, representative-user observations, and per-version Excel/assistive-technology checks. The next practical research step is the four-task reference-machine pilot above; its results should decide the next performance and usability changes.
